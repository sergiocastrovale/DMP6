# Catalogue Lifecycle Audit — 2026-07-31

> Prioritized fix plan with checkboxes. A follow-up agent executes items top-to-bottom.

## Context

The download → merge → catalogue pipeline is the core of the app's business model and must be
bullet-proof. This audit traces the full lifecycle end-to-end, finds correctness bugs, missing
critical test coverage, and product decisions that were made implicitly in code. The pipeline is
mature and mostly solid — the failures are concentrated in (a) a completeness rule that silently
discards good deluxe downloads, (b) silent degradation when ffmpeg/transcode fails, (c) the entire
happy-path catalogue write never being exercised against the real Rust binaries in any test.

### Product decisions confirmed with the owner (2026-07-31)

1. **Extra tracks = deluxe/different edition, keep it.** A local copy with MORE tracks than the
   matched MB edition must be treated as *correct*, not incomplete. Sync/enrich should attempt to bind
   to the larger (deluxe) MB edition in the same release group; if none is found, bind the default
   edition and keep the release. Never purge-and-retry a superset copy.
2. **Lifecycle is: SongKong-enrich → index → sync → catalogue.** There is no separate pre-enrich
   approval gate. SongKong enriches file tags first; then the `index` + `sync` binaries add the release
   to the local catalogue and "enrich again" by connecting it to MusicBrainz. The manual **merge** click
   is the approval. This is the intended model — harden it, don't add a new gate.
3. **Test coverage target: integration + unit + e2e.**

## As-built lifecycle (reference for the fixing agent)

```
topUpDownloads (autoDownload.ts)  → create DownloadedRelease DOWNLOADING, search+acquire (slskd/rutracker)
reconcileDownloads / reconcileTorrentDownloads (monitorLoop.ts)
   transfers done → relocateDownloadedFiles (slskd.ts: move + transcode→mp3-320)
      SongKong enabled → write spool marker → status ENRICHING
         drainEnriching: done-marker or timeout → transformToLibraryLayout (layout.ts) → settleFinished
      SongKong disabled → transformToLibraryLayout → settleFinished
   settleFinished → moveToReady (promote.ts): move into _ready, status READY   [auto, no gate]
merge (manual, or runAutoMergeCycle if enabled):
   mergeDownloadedRelease / mergeManyDownloadedReleases (promote.ts)
      moveIntoLibrary → MUSIC_DIR
      runReconciler('index', --folders)   → creates LocalRelease
      stampMerged: runReconciler('sync', --release [--artist-hint]) → binds LocalRelease.releaseId
         COMPLETE/forcedComplete → PROMOTED + retire MISSING placeholder (by releaseGroupId)
         else → PURGE files + delete LocalRelease + INVALID/ABANDONED   ← problem area
reject / cancel / requeue / force-retry: state transitions in promote.ts + autoDownload.ts
```

## P0 — Correctness / silent data quality

### [x] 1. Deluxe / EXTRA_TRACKS downloads are silently purged and eventually ABANDONED
`stampMerged` promotes only when `matchStatus === 'COMPLETE'` (or `forcedComplete`), otherwise it
**deletes the library folder + LocalRelease and marks the row INVALID→ABANDONED**
(`web/server/utils/promote.ts:219-303`, gate at `:223`, discard at `:277-303`). A superset copy
(complete album + bonus tracks) binds the base MB edition, gets `matchStatus = EXTRA_TRACKS`, and is
destroyed — then re-fetched forever until the attempts cap. Deluxe editions are the common case on
trackers, so good downloads are being thrown away in production.

Per decision #1, implement:
- **Rust matcher** (`scripts/sync/src/main.rs` Tier 1/2 at `:1025-1161`, `status.rs:83-201`): when the
  local track count exceeds the Tier-1-bound edition, browse the release group and prefer a sibling
  edition whose track count equals the local count (the deluxe). `check_release_status` already picks an
  exact-count sibling when browsing a group (`status.rs:102-149`); extend Tier 1 so a count mismatch
  falls through to the group browse instead of binding the base edition outright. If no larger edition
  matches, bind the default edition and record status `EXTRA_TRACKS` (kept, not an error).
- **Promote gate** (`promote.ts:223`): treat `EXTRA_TRACKS` as promotable
  (`complete = matched && (forcedComplete || matchStatus === 'COMPLETE' || matchStatus === 'EXTRA_TRACKS')`).
  Keep purging only genuine `INCOMPLETE` / `MISSING_TRACKS` (fewer tracks than MB).
- **Placeholder retirement**: an EXTRA_TRACKS promote must still retire the MISSING placeholder
  (`promote.ts:238-242`) so it isn't re-downloaded.
- Tests: see items 6 and 11.

Open question flagged below (Q1) on the exact DB status semantics for "kept superset".

### [x] 2. Transcode failure is swallowed; no ffmpeg pre-flight; layout only handles mp3
`relocateDownloadedFiles` calls `transcodeDirToMp3320(...).catch(warn)` (`web/server/utils/slskd.ts:330`)
— a transcode failure (ffmpeg missing, codec error) is logged and ignored, and the release proceeds
with un-transcoded files. `transformToLibraryLayout` then only relocates `ext === 'mp3'`
(`web/server/utils/layout.ts:82`) and dumps everything else as a basename "extra" — so a FLAC that
never transcoded is not laid out as a track, producing a malformed release that later gets INVALID
(track-count mismatch) or a messy catalogue entry. `ffmpegAvailable()` exists but is **never called**
(`web/server/utils/transcode.ts:170`, zero callers).

Fix:
- Wire `ffmpegAvailable()` into a startup/finalize pre-flight; if ffmpeg is absent, log once and pause
  acquisition (or refuse to finalize convertible files) instead of silently degrading.
- In `relocateDownloadedFiles`, if convertible source files remained un-transcoded, fail the attempt
  (retry) rather than returning `movedCount > 0` and marching a broken release to READY.
- Tests: item 9 (transcode-failure branch).

### [x] 3. Shared-releaseId wrong-bind risk (systemic sync-matcher)
Historic state: ~13,325 MB releaseIds each owned by >1 unrelated LocalRelease
(`memory: project_shared_releaseid_mismatch`). The audit-#24 guard
(`scripts/sync/src/main.rs:1198-1215`) only refuses a NEW cross-artist bind when the owner is a
different artist AND titles are dissimilar (`names_are_similar`). It does **not** guard
same-artist-different-album collisions, and `names_are_similar` can false-positive on genuinely
different albums. In the download path a wrong bind means a release is PROMOTED as COMPLETE against the
wrong MB edition — wrong catalogue status, wrong track links.

Fix (scoped — full matcher rework is out of scope):
- Tighten the guard to also refuse binding when the same MB `releaseId` is already owned by a
  *different* LocalRelease of the *same* artist with a different `folderPath` (log + leave Unmatched).
- Add a Rust unit test for `find_release_owner` + the guard predicate (pairs with item 10).
- Confirm the one-off repair (`sync --repair-shared-release-ids`) has been run against live data and
  the count is near zero now; if not, schedule it.

## P1 — Robustness / concurrency

### [x] 4. `mergeDownloadedRelease` (single) has no status guard and no concurrency claim
`mergeDownloadedRelease` (`promote.ts:310-342`) checks only `!row.stagingPath` (`:313`) — it will merge
a row of ANY status (PROMOTED/FAILED/INVALID), and two concurrent merges of the same READY row
(manual double-click, or a manual merge overlapping `runAutoMergeCycle`) both run `moveIntoLibrary` +
index + sync. It is *mostly* idempotent (libExists-recover at `:157-166`, P2002 guard at `:249-255`),
but there is a real race on the physical move + DB writes. `mergeManyDownloadedReleases` already filters
`status: 'READY'` (`:355`); the single path does not.

Fix: filter to READY (throw 409 otherwise) and claim the row before work — either an in-process
`merging` Set mirroring `finalizing`, or a DB claim `updateMany({ id, status: READY } → { status: MERGING })`
returning count (skip if 0). Prefer the DB claim so it holds across the auto-merge cycle and multiple
web instances (merge endpoints run on non-primary instances too).

## P3 — Minor / cleanups

### [x] 5. GC sweeps never run on a schedule → download table bloat
`sweepDanglingDownloads` + `cleanupReadyDownloads` (`promote.ts:520-573`) are invoked **only** by the
manual `POST /api/downloads/cleanup` endpoint (`web/server/api/downloads/cleanup.post.ts`). The monitor
tick (`web/server/plugins/monitor.ts:51-95`) never calls them, so terminal/dangling rows accumulate —
the exact bloat these functions were written to fix (`docs/downloader_issues.md #3,#8`). Every
`/downloads` poll pays for it.

Fix: call `sweepDanglingDownloads()` on a throttled cadence inside the tick (fire-and-forget, guarded,
e.g. every 6h alongside the monitorEvent prune at `:52-56`). `cleanupReadyDownloads` must stay
NAS-guarded (it throws 409 off-volume) — gate it behind the same primary/volume check before scheduling.

### [x] 13. `moveToReady` year==null → mark terminal, not plain FAILED
`moveToReady` (`promote.ts:83-91`) sets a no-year erroneous release to FAILED without bumping attempts
or going terminal. `pickRetry`/`pickFresh` filter `year IS NOT NULL` so it won't re-pick, but the row
lingers in the Failed tab. Prefer ABANDONED (terminal, explicit) so it reads correctly.

### [ ] 14. Detached fire-and-forget acquire in `forceRetryDownload` / `topUpDownloads`
`forceRetryDownload` runs the search in a floating `(async () => {...})().catch(...)`
(`autoDownload.ts:120-135`). A restart mid-search parks the row DOWNLOADING with `files: []` until the
3-min ORPHAN grace fails it (reconcile recovers it). Acceptable — document the recovery path; consider a
shorter orphan window for force-retries. Low.

> **Status:** reviewed, left as-is per its own "Acceptable" scoping — no code change made. The recovery

Resolved by item 2 (wire it). If item 2 opts for a different gate, delete the unused export

## What I'm most concerned about (ranked)

1. **Item 11 / no real-binary test.** "Catalogue updated correctly" is the whole business, and *nothing*
   in CI exercises the real index+sync path. A regression in arg handling or the matcher ships silently.
2. **Item 1 / deluxe purge.** Good downloads have been destroyed and re-fetched in a loop — active data
   loss + wasted bandwidth, happening now.
3. **Item 2 / silent transcode degradation.** No ffmpeg gate anywhere; a broken/missing ffmpeg quietly
   produces malformed releases that poison the catalogue.
4. **Item 3 / shared-releaseId.** Wrong binds mean wrong catalogue truth for both releases; hard to
   notice, corrosive over time.
