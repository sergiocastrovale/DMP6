### Item #24 — shared releaseId repair (2/3 done, repair NOT run)

Status:
1. ✅ **Forward guard shipped** (commit `fix(sync): guard against binding a shared MB releaseId onto an
   unrelated artist`, 2026-07-31). `scripts/sync/src/db.rs` adds `find_release_owner()` (queries any OTHER
   `LocalRelease` row already bound to the same `releaseId`, plus its credited artist ids via
   `LocalReleaseArtist`). `scripts/sync/src/main.rs` calls it right after `upsert_mb_release` returns
   `mb_db_id`, before `ensure_mb_release_artist_link`/track-linking/`update_local_release_match`. If an
   owner exists, is NOT credited with the current `artist.id`, AND its title isn't `names_are_similar()`
   (existing Jaccard word-overlap helper in `mb_matching.rs`) to the current local release's title →
   `mark_local_release_unmatched` + warn log + `continue` (skip binding). Same-artist re-syncs and
   near-duplicate titles still bind normally — only genuinely unrelated collisions are blocked. Built
   clean with `cargo build --release -p sync` (0 errors).
2. ⬜ **NOT DONE: one-off repair for the ~13,325 existing bad rows.** The guard only stops *new* damage;
   existing conflicts stay conflicted until something unbinds the losers. Not built or run — network
   blocker, and user chose to defer rather than have it built blind.
3. ⬜ **NOT DONE: partial unique index** (audit's step 3 — "allow N locals per MB release ONLY for same
   artist set"). Deferred until data is clean (doing it before repair would just fail on the dirty rows,
   or (if made non-unique/deferred) do nothing).

**Design notes for step 2 (write this next), so it doesn't need to be re-derived:**

- Delivery mechanism decided during this session: **add a new sync CLI flag**
  (`./sync --repair-shared-release-ids` with a `--dry-run` mode), following the exact pattern of existing
  one-off flags like `--catalogue-gaps` / `--only-write-mb-to-files` in `scripts/sync/src/main.rs`'s `Cli`
  struct (see `#[arg(long, help = "...")]` entries around line 36-68). This was chosen over a standalone
  script or raw SQL specifically so the user can run it the normal way (`./sync ...` locally or on the
  NAS) without any special setup.
- **Query to find conflicts** (read-only, safe to run any time to check current scope):
  ```sql
  WITH grouped AS (
    SELECT lr."releaseId", array_agg(DISTINCT lr.id) AS local_ids, count(DISTINCT lr.id) AS n
    FROM "LocalRelease" lr
    WHERE lr."releaseId" IS NOT NULL
    GROUP BY lr."releaseId"
    HAVING count(DISTINCT lr.id) > 1
  )
  SELECT count(*) AS conflicting_release_ids, sum(n) AS total_local_rows_involved FROM grouped;
  ```
  This was never actually run against the real DB in this session (blocked by the network issue above) —
  the "13,325" figure is from the audit doc / prior memory, not freshly verified. **Run this first** to
  confirm current scope before writing the fix loop.
- **Per-conflict-group repair logic** (the "unbind losers" step): for each `releaseId` with >1 owning
  `LocalRelease`, need a "who wins" rule. Audit's suggested rule: keep whichever LocalRelease has the
  *better title/track-count match* to the MusicBrainzRelease, unbind (`releaseId = NULL`,
  `matchStatus = 'UNMATCHED'`) the rest so they re-match cleanly on next `./sync`. Concretely:
  - Track-count match: compare `count(LocalReleaseTrack WHERE localReleaseId = X)` against
    `count(MusicBrainzReleaseTrack WHERE releaseId = <the shared releaseId>)` — exact match wins over
    partial.
  - Title match: reuse `names_are_similar()` (now exported from `mb_matching.rs`, already used by the new
    guard) between `LocalRelease.title` and `MusicBrainzRelease.title` — similar-title wins over
    dissimilar when track counts tie.
  - On a genuine tie, prefer the most-recently-synced row (`updatedAt DESC`) as a tiebreaker, or just flag
    for manual review (dry-run should print these, not auto-decide).
- Must NOT touch rows where every claimed owner shares an overlapping artist (legitimate: e.g. a
  compilation credited to the same artist twice via different `LocalReleaseArtist` links) — only
  unrelated-artist conflicts are the bug.
- **Safety**: `--dry-run` must print every conflict group (releaseId, all owning LocalRelease ids/titles/
  folderPaths, computed winner, losers) with ZERO writes, so the user can eyeball it before the real run.
  Wrap the real run in a single DB transaction per conflict group (not one giant transaction for all 13K —
  a mid-run failure shouldn't roll back groups already fixed).
- After running for real: re-run the analysis query above — `conflicting_release_ids` should drop to
  (ideally) 0, or at least explain any remainder (e.g. genuine same-artist duplicates that are fine as-is).

the whole point of #2's fix, migrations must fail loud, not silently `--accept-data-loss`).

**Resume, in order, once the NAS/DB is reachable**:
1. `cd web && DATABASE_URL=<real url> pnpm exec prisma migrate resolve --applied 20260731101731_baseline`
   — tells Prisma "this migration's changes already exist, just record it as applied" WITHOUT running its
   SQL. This is the standard Prisma recipe for adopting migrations on an existing `db push`-managed
   database.
2. Verify: `DATABASE_URL=<real url> pnpm exec prisma migrate status` should report the baseline as applied
   and 0 pending.
3. Only after that succeeds: switch `deploy`'s DB step from `prisma db push --schema=prisma/schema.prisma`
   to `prisma migrate deploy` (mirrors item #2's fix intent — adopt real migrations instead of push-and-pray
   on the shared DB). Until step 1 runs, leave `deploy` exactly as-is (still `db push`, still safe, just not
   yet migration-tracked) — switching prematurely would break every deploy from that point on.
4. Going forward: schema changes get a real migration (`prisma migrate dev --name <description>`) generated
   and committed alongside the code change, instead of relying on `db push` to reshape the live DB blind.
